# 原版 Minecraft 托管闭环（2026-10-10）

本轮已连接实例中心、云端固定发布版本、玩家电脑上的执行器和中心房间入口。实际 Java 服务端由玩家电脑运行，中心负责账号、授权、唯一托管任务、加入地址和权威存档引用。

## 已实现的流程

1. 管理员或实例所有者发布原版游戏和服务端环境，创建存档并开放它的唯一房间。
2. KAMUCL 中使用社区账号登录，选择存档并点击「由本机托管房间」。托管资格由中心按当前账号和存档范围返回；本机运行资格不授予游戏 OP 或实例管理权限。
3. 启动器使用一次性短期票据启动相邻的 nomad-agent.exe；票据通过文件传递并立即消费，不放在命令行。执行器领取带 epoch 的独占租约，下载已发布的服务端、验证已知 SHA256/SHA1、恢复中心保存的世界，再用对应 Java 启动原版 jar。
4. 服务端只绑定本机回环地址。执行器向中心建立经过票据和 epoch 鉴权的出站 WebSocket 通道；中心提供原生 Minecraft TCP 加入地址，服务端就绪后才公布。KAMUCL 的「同步并启动」会再次检查存档固定版本和房间地址，并使用原 KAMUCL 的启动与正版认证流程。
5. 默认每 120 秒执行 save-off → save-all flush → 打包 world/ → save-on → 上传检查点；打包确认来自真实服务端日志。ZIP 使用快速压缩，上传期间恢复自动保存。中心逐条验证文件路径、类型、展开大小和重复路径，仅接受世界内容，拒绝 ops.json 等策略文件注入。
6. 关闭房间、撤回托管授权或点击「停服并回传存档」后，执行器请求 Java 正常停服，再上传标记为最终保存的世界；中心必须收到当前 epoch 的最终检查点才能确认干净释放。中心停止请求后的回传租约持续续期，但限定在十分钟内；超时不允许旧 epoch 覆盖新执行器的存档。
7. 新执行器从中心最近提交的权威 ZIP 恢复。正常停服使用最终版本；异常失联只能恢复最近成功的检查点，因此检查点之后的进度可能丢失。本地世界和待回传 ZIP 在失败时保留。

## 权限和持久化

票据在中心只存 SHA256 哈希，原始 token 不出现在实例列表里。票据签发、领取、心跳、隧道和上传前检查当前账号；撤权关闭转发通道。仅同一存档当前 epoch 可提交世界。执行中和停止回传中禁止更换固定发布版、修改相关运行策略或重新开放房间，以免旧进程和新配置重叠。

元数据使用既有 Storage 适配器，支持本地和 Redis；world ZIP 保存在 panel/data/NomadWorlds/<sha256>.zip。备份时同时保留 NomadCatalog、NomadPackages、NomadServerArtifacts 和 NomadWorlds。多中心共用 Redis 时，也必须共用这些文件目录；跨面板进程的分布式租约锁与转发调度尚未实现，此闭环应由单个中心进程管理。

管理员上传限额继续默认 5 GiB，可在设置里更改；执行器领取恢复大小限制时使用中心当前配置。中心还限制展开大小和条目数。世界快照目前是完整 ZIP，尚未接入旧 Rust 快照引擎的增量块同步；大型世界和慢速网络的耗时仍需专项验证。

## 如何查看

网页预览：http://127.0.0.1:5173/index.html#/catalog 。内嵌网站和 API：http://127.0.0.1:23333 。新版静态页面已复制到 panel/public，原有账号和数据保留。

启动器：vendor/kamucl/release/KAMUCL-1.1.22.exe 。请保留旁边的 DLL、config、runtimes 和 nomad-agent.exe。新增控制使用 KAMUCL 的 Vue 组件；源码在 vendor/kamucl/src，可复现补丁在 vendor/kamucl。正版账号入口保留，社区账号不代替 Minecraft 正版账号。

操作顺序是：发布原版实例 → 创建并配置存档白名单 → 开放房间 → 托管成员在 KAMUCL 登录社区并选择该存档 → 本机托管 → 查看实例中心加入地址 → 玩家同步并启动。托管电脑需要对应版本 Java，服务端发布必须接受 EULA。

默认中心 TCP 转发仅绑定并公布 127.0.0.1，供本机审阅。管理员可设置转发绑定地址和公网域名/IP；远程执行器连接要求 HTTPS，代理要支持 WebSocket。每次托管任务分配临时 TCP 端口，跨主机切换后的固定地址、公网端口范围和公网穿透部署尚未完成。

## 实际验证

scripts/verify-vanilla-hosting.mjs 会启动隔离的真实面板，使用正常账号会话发布 Minecraft 1.20.1，运行实际 Java 21 服务端，通过中心转发进行原生协议状态查询和白名单玩家登录，验证周期回传、独占租约和正常停服最终回传，再启动第二个独立目录中的执行器恢复同一世界并再次连接。世界中写入的验证标记随权威存档恢复。报告在 docs/proofs/vanilla-hosting-2026-10-10.json。

两次执行器都运行在本机，不是跨两台物理电脑或公网验证。隔离测试专门设 onlineMode=false，玩家 OP 为零；它证明真实 Minecraft 进程、转发和存档链路，不代表已完成微软正版账号的登录验证。正常服务端设置仍默认 onlineMode=true。

验证结果：panel 86 项测试（含真实 HTTP 和隧道检查）；frontend 66 项测试、类型检查和生产构建；nomad-agent 15 项单元测试与 3 项真实 HTTP 测试；common 9 项、daemon 144 项测试；完整 common 集成联调的 auth、user、instance、files、streams、security_user、security_instance、security_files、security_auth 九组通过，Docker 在 Windows 跳过。KAMUCL C#/WPF 构建和 C# 客户端检查通过。大区块 ZIP 读取阻塞已用两 MiB 随机数据回归检查覆盖。

本轮原生 KAMUCL 托管按钮已编译接入；完整游戏闭环由 Rust 执行器直接驱动验证。环境自动审核拦截了复制并启动新版 EXE 的组合命令，仅返回 blocked by policy；随后单独同步发行文件并核对了执行器哈希，未声称已手动点击新版原生界面完成全部流程。

## 后续范围

当前执行器只执行 vanilla 发布；Paper、Fabric、Forge、NeoForge 的服务端解析和下载基础已有，但安装、服务端专用模组与真实托管还没有接入这一执行路径。微软应用资格和真实玩家账号认证、跨物理主机公网测试、固定房间地址、异常断线恢复和增量存档同步继续作为后续工作。

拥有系统控制权的计算者仍可改动自己的 Java 进程。本轮实现中心端权限、云端策略下发和旧任务提交隔离，未实现对恶意执行者的密码学证明。
