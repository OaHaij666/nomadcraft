# 本地扩展与运行数据同步设计（2026-10-10）

状态：需求分析与改造设计。本次只记录方案，尚未修改启动器校验、下载 UI 或服务器存档协议。

## 最新产品决策

用户已确认朋友间互信、不做反作弊、采用正常保存后搬迁恢复。以下早期全面分类/严格控制方案作为问题分析保留；第一版按发布组件清单做完整性检查，不为每个 MOD 推断关键配置，不封锁个人资源或正常运行数据，不把 config 或 OP 变化当作作弊。以 [产品愿景](产品愿景.md) 的“朋友间互信与朴素交接”为准。当前全目录指纹尚未修改。

## 云端配置边界补充

不做反作弊不等于 config 任意成为正式版本。云端明确发布的配置文件保持中心版本，候选节点预下载、启动前确认；本地主机改动不自动覆盖中心。个人配置和运行数据保留。具体同步时序、恢复优先级和待实现项见 [同步范围与云端配置版本](同步范围与云端配置版本.md)，该补充优先于早期“所有配置首次提供”的简化建议。

## 已确认的问题

vendor/kamucl/src/main/core/nomadCloud.ts 的 InstalledFiles 将 mods、config、resourcepacks、shaderpacks、defaultconfigs、kubejs、scripts、datapacks 整目录递归哈希；根目录 jar/json 也参与。InstallationIntact 用整份 files 的 DeepEquals 判断一致。NomadView.vue 的同步流程在不一致时将旧版本目录移动到 .previous-* 再安装。

因此，在受检目录中新增资源/光影包、生成数据库、改写初始化配置，都可能触发重装；旧目录虽保留，用户数据并未自动迁回新目录。当前也没有对这些差异的分类解释。

apps/agent/src/hosting.rs 的 snapshot_world 只打包 world/，面板 nomad_worlds.ts 也只接受 world/。服务端模组将持久数据写在其它位置时，当前迁移不会覆盖它；本轮执行器的真实闭环仅支持 vanilla，不能把现有能力写成已支持模组外部数据库迁移。

## 文件归属和规则

规则同时声明用途、归属、可变性和生命周期。客户端安装指纹、个人资源同步、服务器检查点分别处理，不能共用一张忽略扩展名列表。

| 类别 | 示例 | 同步与校验规则 |
| --- | --- | --- |
| 云端固定环境 | MC/加载器、必需 MOD、游戏规则配置、服务端脚本 | 根据发布清单校验指定文件；必需项变化才产生环境冲突；服务端脚本等可执行新增项单独识别 |
| 云端初始值 | 客户端默认配置、默认按键、首次附带资源 | 初次安装提供种子；游戏正常改写后保留本地；后续默认值更新需有迁移或提示 |
| 个人外观和允许的扩展 | 光影、材质、截图、画质、经策略允许的客户端 MOD | 允许本地下载、导入、切换、删除；不计入共享玩法版本指纹；同步/修复保留 |
| 客户端运行数据 | 小地图、个人标记、缓存、SQLite、MOD 本地数据 | 不按固定发布文件比对；有价值数据持久保留，临时缓存可重建；个人云备份另设明确开关 |
| 房间服务端运行数据 | 世界、模组进度、领地、经济、SQLite 等 | 中心持有权威检查点，按房间存档迁移；不能因数据库后缀被当作私人本地数据忽略 |

同目录可混合这些类型，特别是 config/。管理员或整合包作者应能指定精确路径/目录前缀和配置职责，不能笼统锁死所有配置，也不能直接放开游戏规则配置。具体客户端/服务端配置由适配规则给出，不能凭名字猜测。

## 光影、材质与客户端 MOD

云端继续管理实例和必需整合包；启动器保留“本地外观与扩展”入口。可下载/导入光影与资源包，显示来源、版本和当前实例兼容性，不改变房间固定发布版。必需加载器或渲染 MOD 仍通过云端发布/可选组件管理，下载一个光影包不应悄悄改动共享 MOD 清单。

服务方可发布推荐/可选资源，用户选择安装；确有必需资源的整合包可声明必需文件，校验这些指定文件也不意味着禁止用户添加其它资源。资源有冲突或优先级要求时明确显示。

可选客户端 MOD 作为整合包兼容选项处理，允许朋友按发布环境协商使用；未知新增 jar 可提示兼容性，不承担反作弊拦截。Fabric environment=client 等元数据可辅助做兼容分类，但不是代码可信或反作弊证明。下载资源要显示许可/来源并遵循提供方下载接口，第三方下载源接入待实现。

## SQLite 与运行时文件

不以 .db/.sqlite 后缀作为所有权结论，也不把固定哈希发生变化解释成作弊。模组可使用其它文件名或格式，识别依赖运行数据注册和路径规则。

SQLite 可能同时使用主数据库、-wal、-shm，回滚模式还可能有 -journal。任意时刻独立复制主文件和 WAL 不能保证一致快照。客户端个人备份应在游戏关闭、连接干净关闭后进行，或由适配器使用 SQLite Online Backup API 等一致备份方法；不要自行删 WAL 或对任意数据库强制 checkpoint。

服务端数据库必须与世界在相同逻辑检查点冻结/导出，并随同一份独占租约和 epoch 提交。单个 SQLite 的一致备份仍不证明它和 Minecraft 世界处于同一逻辑时刻；需要模组刷新钩子、停写屏障或干净停服。无合适钩子时，先支持停服迁移，不宣称在线一致迁移。

外部 MySQL/Redis 等持久服务需要单独适配，不归入任意本地文件抓取。权限变更继续由中心控制面授权；授权节点提交数据库文件不证明恶意运行者没有修改内容。

## 校验、修复和升级

1. 清单只记录固定环境应管理的文件和可执行扩展边界；本地资源层/运行数据不参与固定环境指纹。
2. 按来源和规则报告“必需组件变化”“个人资源变化”“运行数据更新”“未知文件”，而非一个环境损坏布尔值。
3. 未知文件默认保留并提示分类；若落在被运行时加载的 MOD/脚本位置，单独执行扩展授权检查，不因为名字叫数据库就绕过限制。
4. 同步/修复只替换云端负责的文件，保留个人资源和运行数据；游戏运行时不移动目录或覆盖数据库。
5. 发布版独立目录照旧。跨版本迁移个人配置和数据需按实例/模组兼容性处理；不自动在不兼容版本間共享同一个活跃数据库。
6. 旧的全目录指纹不能直接变成新规则的可信基线，应由发布清单/受验证安装生成新基线。迁移先保留旧目录，禁止把当前本地环境重新记录为云端固定版本来掩盖变化。
7. 个人内容默认不上传给社区中心；跨设备个人备份属于独立选择，存档检查点只收集房间明确声明的服务端数据。

## 验收场景

- 新增/删除/修改个人光影、材质包，重启同步不触发重装、不删除个人资源。
- 服务方声明的必需资源损坏能修复，同时保留额外个人资源。
- config/ 下新建数据库或已声明数据库产生 WAL、JSON 缓存/小地图数据，不触发环境误报。
- 已发布必需组件缺失或损坏仍能修复；额外 MOD/脚本作为兼容性变化显示，不因本地扩展或游戏管理操作判定作弊。
- 云端初始配置被模组正常改写可以保留；真正的游戏规则配置仍按策略管理。
- 更新/修复/更换服务时数据隔离正确，运行中数据库不被复制覆盖；旧格式升级不丢数据。
- 个人数据库不默认上传；服务端世界目录外的已登记数据库参与同一存档检查点，在新计算节点恢复。
- SQLite 有 WAL、文件占用、干净停服和备份失败时都不会假报成功；跨世界/数据库快照不一致时禁止交接提交。
