# 现有轮子调研 —— 别造轮子，先抄对答案

> 结论先行：**我们设计的架构，三天前刚有一个开源项目几乎 1:1 实现了一遍（varde）。**
> 更重要的发现：**入口路由、反向隧道、P2P 打洞、增量快照、服务端生命周期管理——每一块都有成熟轮子，我们几乎不用自己写核心算法。**
> 本文档给出：可复用清单、许可证红线、复用决策表、以及"我们到底还要自己写多少"的诚实答案。

- 日期：2026-10-08
- 前置：`技术研究-v1.0.md`（架构设计）、`需求分析-v0.1.md`
- 调研方式：GitHub API 实查，数据为查询时刻真实值

## 0. 三条最重要的结论

### 结论 1：varde = 我们蓝图的成品实现（但有毒）

`grendalaget/varde` 的架构与我们 `技术研究-v1.0.md` 里设计的东西**几乎逐条对应**：

| 我们的设计 | varde 的实现 | 状态 |
| --- | --- | --- |
| Coordinator（公网、无游戏） | `varde-control-plane`（Go，可嵌 UI/relay） | 已有 |
| Relay（纯转发、无游戏） | `varde-relay`（Go，forwards bytes only） | 已有 |
| 玩家侧 Agent | `varde-agent`（Rust，Windows 服务/systemd） | 已有 |
| 反向隧道 / 出站连接 | QUIC mesh + relay fallback | 已有 |
| 租约 + epoch + 防脑裂 | I1/I2/I3 不变量 + self-fencing | 已有 |
| 世界快照 + 增量 + 原子提交 | BLAKE3 内容寻址 + FastCDC 分块 + zstd | 已有 |
| 固定连接地址 | `127.77.0.0/16` 稳定 loopback IP | 已有 |
| 世界副本/备份 | Anchor 节点 + 复制因子 | 已有 |
| 模组/游戏适配 | `games/` driver 插件（已含 minecraft） | 已有 |

**但是——三个致命前提：**

1. **太新**：仓库创建于 **2026-10-05**，到今天才 **3 天**。325 个文件、0 star、0 fork、0 issue。**这是刚出炉的代码，没经过任何实战检验。**
2. **许可证是 AGPL-3.0**：`2026-10-06` 刚从 MIT **改成 AGPL-3.0**。AGPL 有强传染性——如果我们抄它的代码且对外提供服务，**必须开源我们自己的全部代码**。
3. **我们无法验证它是否真能跑**（3 天的新项目，测试覆盖未知）。

**用法建议**：**当"参考答案"读，不当代码库抄。** 学习它的架构决策、踩坑记录、不变量设计（这些是最有价值的），但关键代码自己写或换成 MIT/Apache 的轮子。

### 结论 2：我们的"不用代理"路线，被一个 MIT 项目独立验证了

`scrayosnet/passage`（Rust，MIT，17 star）明确写了：

> While traditional Minecraft networks relied on proxies like BungeeCord, Waterfall or Velocity, Passage is **only an entrypoint and initial router and drops the connection to the player right after the routing**, improving performance and reliability.

它利用的是 **Minecraft 1.20.5+ 官方 Transfer 包**：入口只负责鉴权 + 路由，然后把玩家"弹"到真正的后端服务器，**自己根本不持续转发流量**。

**这证明了：**
- 我们的"公网节点不做游戏逻辑"方向是对的；
- 而且还有比"持续 TCP 中继"更省资源的做法——**无状态入口路由器**；
- 代价：仅支持 1.20.5+，且需要后端能接受 transfer。

### 结论 3：真正需要我们自己写的，只有"胶水 + 策略"

整理下来，核心算法全都有现成实现：

- 反向隧道 -> **frp / rathole**
- P2P 打洞 + 中继兜底 -> **iroh / libp2p / quic-go**
- Minecraft 连接入口 -> **mc-router / passage**
- 增量世界备份 -> **fastback / restic / rclone**
- 服务端生命周期 -> **docker-minecraft-server / Pterodactyl wings**
- 快照去重 -> **restic / casync / borg**

**我们真正要写的，是"把上面这些拼起来 + 主机选举策略 + 世界一致性协议"这一层胶水。** 这正是"用别人的才是王道"的最佳落点。

3. **许可证会变** —— varde 三天内就从 MIT 改成了 AGPL。**不要依赖"现在是 MIT"就放心大规模抄**，尤其对个人新项目。

## 4. 深入剖析：varde（值得我们逐条学习）

即使不抄代码，它的设计**直接回答了我们技术文档里所有"怎么做"的问题**。以下是它公开的设计要点：

### 4.1 组件划分（与我们完全一致）

    varde-control-plane  (Go)   <- 协调，无游戏逻辑，SQLite/Postgres，内嵌 UI 和 relay
    varde-relay          (Go)   <- 只转发字节，无游戏逻辑，可多区域
    varde-mesh           (Go)   <- 每台机器上的 QUIC mesh（agent 的子进程）
    varde-agent          (Rust) <- 服务管理、存储、执行器
    varde-tray           (Rust) <- Windows 托盘 + Fluent 2 桌面应用

### 4.2 它的 10 条不变量（我们直接抄作业）

| | 不变量 | 强制手段 |
| --- | --- | --- |
| I1 | 每个服务器 <= 1 个有效执行 epoch | 唯一索引 + 单调 epoch，旧租约失效才发新租约 |
| I2 | 无租约 => 不许托管 | Agent 自算 self-fencing 截止时间 |
| I3 | 过期 epoch 永不发布"权威状态" | 每次写入带 (server_id, execution_id, epoch, node_id)，不符则 409 |
| I4 | 自动恢复只能用 committed 快照 | 调度器过滤 state=committed |
| I5 | Manifest 不可变 | snapshot_id = BLAKE3(manifest) |
| I6 | Chunk 使用前必须校验 | 每次读写都验 BLAKE3 |
| I7 | 主机变更 != 地址变更 | 每服务固定 loopback IP，路由按 service_id |
| I8 | 协调面丢失不损坏已存状态 | Agent 只按显式指令删快照；恢复先写 staging 再 rename |
| I9 | 无远程 shell | 指令是强类型结构化，driver 组装 argv，永不调 shell |
| I10 | Windows 干净安装零配置 | 服务空转直到配对 |

**这套不变量就是我们技术文档 4.1 节「防脑裂」的工业级表达。建议直接采用。**

### 4.3 它的快照设计（可直接照做）

- **内容寻址分块**：FastCDC（min 256KiB / avg 1MiB / max 4MiB），chunk id = BLAKE3(明文)。
- **压缩**：zstd level 3，先写 `tmp/` 再原子 rename。
- **Manifest**：规范 JSON（key 固定顺序、files 按 path 排序、无多余空白），`snapshot_id = snap_ + base32(digest[0..16])`。
- **路径安全**：拒绝 `..`、绝对路径、盘符、NUL、Windows 保留名（CON/NUL…）、结尾点/空格——**Windows 兼容必须做**。
- **生命周期**：`local -> replicating -> committed -> superseded`，`invalid` = 校验失败或被 fenced。
- **提交策略**：`ready_replicas >= min_commit_replicas`，可选必须有 anchor。
- **传输**：不走控制面，走 mesh 的 HTTP 内部服务（`agent.chunks`），接收端逐块验证。

### 4.4 它的网络设计（关键创新：无 TUN 的稳定地址）

- **稳定地址**：每个服务分配 `127.77.0.0/16` 里的一个 loopback IP（`offset = fnv32a(service_id)`）。**玩家永远输入 `127.77.12.34:25565` 这种地址，主机换了也不变。** Windows/Linux 的 127/8 都是 loopback，无需配置。
- **客户端侧**：每个节点都绑定这些 loopback 地址的监听（包括主机自己），服务停了也保持绑定 -> 地址永不漂移。
- **主机侧**：mesh 只接受当前 `(service_id, epoch)` 的流，否则回 `STALE_EPOCH` -> **过期路由直接被拒**。
- **UDP**：按客户端源地址分 flow，走 QUIC datagram -> **覆盖了语音模组的 UDP 问题**（我们文档里标为待解决）。

> 这四个设计点，我们几乎可以**原封不动地采用**（重新实现，不是抄代码）。

### 4.5 它的游戏驱动（模块化）

- 核心代码**零游戏逻辑**，游戏行为在 `games/` 下的 driver crate 里，接口是 `crates/game-driver-api`。
- 已实现：`games/minecraft`、`games/valheim`、`games/testgame`。
- 控制面只知道一个**数据目录**（id、显示名、端口、配置 schema、资源提示）。
- **我们要做的就是写好我们的 minecraft driver。**

## 5. 我们到底还要写多少？（诚实评估）

| 模块 | 现成轮子 | 自研量 | 难度 |
| --- | --- | --- | --- |
| 入口路由 | mc-router / passage | 动态后端联动 | 低 |
| 反向隧道 | frp / rathole | 与租约联动 | 低 |
| P2P mesh | iroh / libp2p | 选路策略 | 中 |
| 连接多路复用 | smux / yamux | —— | 极低 |
| 服务端生命周期 | docker-minecraft-server（思路） | Windows 进程管理 | 中 |
| 快照格式 | 参考 varde 设计 | Minecraft 一致性 | 中高 |
| 增量同步 | rsync/FastCDC | region 适配 | 中 |
| 对象存储传输 | rclone | —— | 低 |
| **协调 / 选举 / 租约** | **无** | **全自研** | 高 |
| **世界一致性协议** | **无** | **全自研** | 高 |
| 管理面板 | MCSManager | 对接 | 低 |

**结论：整体工作量里，大约 60-70% 有现成轮子可复用，我们真正要攻的只有"协调 + 一致性"这两块。**

## 7. 立即可执行的三步

1. **拉 varde 源码当作"设计字典"通读一遍**（`docs/architecture/` 五个文档最值钱），把它的 10 条不变量、快照格式、loopback 地址方案记录下来，**转写成我们自己的规格**。
2. **跑通一个 mc-router + 现成 Minecraft 服务端的最小实例**，确认入口路由可用、延迟可接受。
3. **用 frp 或 iroh 做一次"玩家机器出站接入 -> 公网节点转发"的 spike**，验证 R1 落地。

**这三步不需要写多少新代码，全部在"拼现成轮子"，符合"用别人的才是王道"。**

## 8. 风险提醒

1. **varde 只有 3 天历史** —— 不要把它当作"生产可用的依赖"。
2. **AGPL 陷阱** —— 一旦抄进代码，你的整个项目可能被迫开源。
3. **mc-router 基于 hostname 路由** —— 我们如果做"动态主机切换"，需要改造它或用它的库。
4. **passage 只支持 1.20.5+** —— 如果玩旧版本/旧整合包，这条路走不通。
5. **frp/iroh 解决的是"连通"** —— 主机切换的一致性仍然要我们自己保证。

## 9. 一句话总结

> **别从零写隧道、别从零写 P2P、别从零写入口路由、别从零写快照存储。**
> **把这些 MIT/Apache 的轮子拼起来，我们只专注写"选谁当主机"和"世界怎么不烂"这两件事。**
> **varde 证明了我们的架构是对的，但它自己太新且是 AGPL——所以：读它，别抄它。**
