# 内核改造：从"本机开服"到"协调 + 快照 + 中继"

> 用户要求：完整改造，皮血肉，确保全部符合我们需求。
> 当务之急是改造内核；前端减量后置。
>
> 本次改动只碰一个继承来的入口，其余全部是新增代码。

---

## 一、改的是哪一刀

MCSManager 的 daemon 里，实例启动走这条链：

```text
system_instance.ts → instance.execPreset("start")
  → dispatcher.ts: setPreset("start", new GeneralStartCommand())
  → start.ts: AbsStartCommand.exec()   （状态机 + 磁盘检查）
  → general_start.ts: createProcess()  ← 真正 spawn 游戏进程的地方
```

`createProcess()` 原本无条件在本机 `spawn(java, ...)`。这就是"本机开服"内核。

改造后，它在 spawn 之前必须依次完成：**抢租约 → 追平快照 → 恢复世界**；
进程起来后 **挂中继通道 + 定时检查点**；进程退出时 **提交最终检查点 → 释放租约**。

顺序本身就是设计，每一步都是为了让世界不可能被两台机器同时写入：

| 阶段 | 动作 | 为什么 |
| --- | --- | --- |
| fence | `POST /v1/servers/:id/claim` | 同一时刻只有一台机器持有租约，赢家才能碰存档 |
| catch up | 拉取已提交快照 → 恢复到实例目录 | 新主机必须先拿到最新世界，否则会分叉 |
| serve | 启动进程，向 relay 挂 `SLOT <room>` 通道 | 玩家不需要公网 IP，连 relay 固定域名即可 |
| protect | 每 N 秒快照 → 上传 → `POST .../checkpoint` | 主机崩溃也有可回退的存档 |
| hand over | 最终检查点 → `POST .../release` | 其他玩家几乎无感地接管 |

## 二、新增了什么（全部是"我们的核"）

在 `vendor/mcsmanager/daemon/src/service/nomad/` 下：

| 文件 | 职责 |
| --- | --- |
| `coordinator.ts` | 协调器 HTTP 客户端（注册 / claim / renew / release / checkpoint / manifest / chunk） |
| `snapshot_engine.ts` | 调 Rust `nomad-snapshot` 二进制做分块、快照、恢复、校验；定义"世界包含哪些文件" |
| `snapshot_sync.ts` | 内容寻址增量同步：只上传/下载双方差异的分块 |
| `tunnel.ts` | 主机侧的 relay 通道池：常驻若干 `SLOT` 连接，玩家来了即接通 |
| `session.ts` | **HostingSession**：把上面四件事编排成一次完整的托管周期 |
| `settings.ts` | 从环境变量读配置；未配置协调器时行为与原生 MCSManager 完全一致 |
| `index.ts` | 对外只暴露一个模块入口 |

在仓库根新增一个 Rust 二进制：

| 位置 | 职责 |
| --- | --- |
| `apps/snapshot-cli/`（`nomad-snapshot`） | daemon 的"世界快照引擎"桥。`snapshot` / `restore` / `verify` / `list` / `import-manifest`，JSON 进出 |

### 为什么快照引擎要单独做成二进制

FastCDC 分块边界、BLAKE3 分块身份、**快照 id = manifest 的规范化摘要**、读取时校验——
这些只要有一处在 JavaScript 里"重新实现一遍"，就会出现两个事实来源，
总有一天会不一致，而不一致的后果是**存档损坏**。

所以只保留一份实现（Rust，已有 101 项测试），daemon 通过 JSON 调用它。
TypeScript 侧只负责"快照哪些文件"和"把分块搬到协调器"。

## 三、配置（环境变量）

不配置 `NOMAD_CONTROL_PLANE` 时，daemon 与原版行为一致（照常本机开服），
所以这是一个可回退的改造，而不是一个不能回头的分支。

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `NOMAD_CONTROL_PLANE` | （空 = 关闭协调） | 协调器地址，例如 `http://127.0.0.1:8787` |
| `NOMAD_NODE_ID` | `node_local` | 本机在协调器上的节点 id |
| `NOMAD_SERVER_ID` | 实例 uuid | 本实例对应的协调器 server id |
| `NOMAD_ROOM_HOST` | 实例昵称 | 玩家在 relay 上连的域名 |
| `NOMAD_RELAY_TUNNEL` | （空 = 不开通道） | relay 隧道监听地址，`host:port` |
| `NOMAD_SNAPSHOT_BIN` | `nomad-snapshot` | 快照引擎二进制路径 |
| `NOMAD_STORE_DIR` | `<NOMAD_DATA_DIR>/store` | 本机快照仓库 |
| `NOMAD_TUNNEL_SLOTS` | `4` | 常驻 relay 通道数 |
| `NOMAD_CHECKPOINT_MS` | `120000` | 运行中检查点间隔 |

## 五、已知边界（诚实记录）

1. **一个通道 = 一个玩家**。relay 的 `Registry` 目前每次只取一个 slot。
   多人在线需要 `TunnelPool` 保持多个常驻通道（已实现），但 relay 侧"每房间多 slot"
   的扩容与"主机切换时玩家无感重连"还需要在 relay 里补。
2. **主机崩溃 = 租约到期**。目前靠心跳续租；协调器 `tick()` 到期回收后，
   另一台机器下次 claim 才能接管。主动切换比崩溃切换快得多。
3. **player 认房间靠 `SLOT <hostname>`**。relay 当前按连接时的 hostname 路由；
   "必须先进软件划分的房间、与服务器存档同步后才允许游玩"这层准入还没接到 relay。
4. Docker 路径未改（用户说"docker 后面再说"）。

## 六、第二轮改造（本轮新增）

在上一轮"抢租约 → 快照 → 中继"的基础上，补齐了三个直接决定产品可用性的环节。

### A. 防分叉：检查点必须延续已提交的世界

**动机**：光有租约还不够。一台已经掉线的旧主机、或者恢复到旧存档的机器，
只要 epoch 还没过期，就可能把一份**分叉**的存档提交上去，
把其他人这一段进度悄悄冲掉。

**做法**：协调器在 `commit_checkpoint` 时校验新快照是否**沿 parent 链回溯到当前已提交快照**。

- 新增 `nomad_snapshot::descends_from(store, candidate, ancestor)`：沿 parent 走链，
  自身算祖先；父缺失即"不是后代"（fail closed）；带环/超深保护。
- 新增 `EngineError::ForkedSnapshot`，`api.rs` 里返回 `409 forked_snapshot`。
- 服务器的**第一份快照没有祖先，永远放行**——世界就是这么诞生的。
- 测试：`crates/nomad-snapshot/src/sync.rs`（3 个）+ `apps/control-plane/tests/api_tests.rs::a_checkpoint_that_does_not_descend_is_refused`。

### B. 中继交接：新主机上位即清掉旧主机的通道

**动机**：主机换了以后，旧机器可能还在 relay 上挂着若干"暖通道"（warm slot）。
玩家被塞进这种通道，等于连到了一个不再是权威的旧世界，玩的就是分叉。

**做法**：每条 slot 带上**主机代次令牌**（用租约 epoch 正好）。

- `SLOT <hostname> [token]`，令牌对 relay 不透明，只做相等比较。
- `Registry::park` 在**新代次**第一次放置 slot 时，清除所有**其他代次**的 slot，并返回淘汰数用于日志。
- 旧协议 `SLOT <hostname>`（无令牌）默认 `"default"`，行为与改造前完全一致——向后兼容。
- daemon 的 `TunnelPool` 现在发送 epoch 作为令牌。
- 测试：`apps/relay/tests/relay_tests.rs::a_new_host_evicts_the_previous_hosts_slots`。

### C. 门禁：只能从软件划分的房间进来

**动机**（用户原话）："免得只有单人在线，它偷偷玩刷物资，然后声称这是最新存档请求服务器同步。
我们服务器才不搭理呢——你进我们软件划分的房间，和本地存档同步之后再开始游玩。"

**做法**：房间有成员名单 + 一把门禁开关；控制面签票，relay 验票。

- `nomad-proto::door`：`DoorTicket` + 规范编码 + BLAKE3 keyed 签名 + 常量时间校验 + 有效期窗口。
- 控制面新增接口：
  - `POST /v1/rooms/{id}/join` —— 玩家用软件申请进门，成员才发短期票（默认 60s）。
  - `POST /v1/rooms/{id}/admit` —— relay 在门口问的接口，返回 200/403，**失败即拒**。
  - `GET|POST|DELETE /v1/rooms/{id}/members`、`POST /v1/rooms/{id}/lock` —— 名单与开关。
  - `GET /v1/servers/{id}/room` —— 由服务器反查房间。
- 房间**默认开放**（方便搭建），`members_only` 打开后只放名单内的人。
- relay 侧 `Door`：玩家用 `<player>.<房间域名>` 连接时取首段玩家名，向控制面询问；
  控制面不可达时**fail closed**（拒绝），绝不因为协调器宕机就门洞大开。
- 成员名单随 `engine.json` 持久化，重启不丢。
- 测试：`api_tests.rs`（2 个）+ `relay_tests.rs`（3 个）+ `nomad-proto`（9 个）。

### 仍未做（诚实记录）

1. **relay 侧按房间限流/多 slot 上限**：目前一个主机开多少 slot 就是多少容量，没有按房间设上限。
2. **主机崩溃后玩家无感重连**：现在玩家会掉线重连；"无感"需要 relay 记住会话并重放。
   目前断线后重连即可，存档不会丢（有检查点）。
3. **玩家名的身份强度**：门禁认的是玩家名（Minecraft 用户名可重名/可伪造）。
   真正的强身份要接到 Mojang/Microsoft 登录校验或我们的账户体系，属于后续工作。
