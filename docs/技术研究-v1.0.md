# 玩家自托管 Minecraft Java 服务器 —— 硬核技术研究文档 v1.0

> 目标：把"低配公网节点只做中转与协调 + 计算下放到玩家电脑 + 主机下线可切换"这件事，从想法落到能动手实现的技术方案。
> 风格：结论先行、方案对比、可直接照做的接口与状态机。
> 一句话：**公网服务器不跑游戏、不需要装 Minecraft；它只是"智能门卫 + 快递站"。真正的世界在玩家机器上轮流活。**

---

## 0. 先把三个核心需求钉死（以此为唯一验收口径）

| 编号 | 需求 | 技术含义 |
| --- | --- | --- |
| R1 | **公网节点只做流量中转**，不要求每个人有公网 IP、不要求每人开服 | 公网节点是 L4/TCP 中继 + 信令；玩家侧用出站连接接入，天然穿透 NAT |
| R2 | **从在线玩家中选一个当主机**执行游戏逻辑 | 玩家机器运行真实服务端进程；Coordinator 负责选举、租约、寻址 |
| R3 | **主机下线后其他人不能崩**，相对无感（卡顿可接受） | 世界状态必须持续同步到中转节点；下线触发重选举 + 重放/恢复 |

三条都满足 = 成功。**R1/R2/R3 之外的问题全部不在本阶段范围。**

我们的公网服务器**不安装、不运行、不解析 Minecraft 游戏逻辑**。它可以是一台只有 1 核 512MB 的小鸡，甚至没有固定 IP（靠隧道兜底）。这是本方案最重要的成本优势。

## 1. 结论速览（TL;DR，一屏看完）

1. **架构选型：纯 L4（TCP）中继 + 信令协调 + 玩家侧真实服务端进程。**
   不采用"公网节点跑 Velocity 代理"作为主路线，因为代理会引入模组/加密/握手兼容的地狱级复杂度，且让公网节点重新变成"必须性能好"的角色，违背初衷。

2. **每个玩家装一个 Host Agent（常驻小程序）**，它负责：出站连 Coordinator、按需启动/停止服务端、按时做世界检查点、上报心跳、参与选举。普通玩家和主机跑的是同一个 Agent，只是角色不同。

3. **Coordinator 不跑游戏**：它维护"房间真相"——当前主机是谁、租约版本（epoch）、世界版本号、检查点索引、在线玩家。全部是小数据。

4. **穿透用"反向隧道 + 出站连接"解决**：玩家 Agent 主动向 Relay 建立长连接，Relay 把玩家流量通过这条已建立的连接转发给主机。**主机永远不需要公网 IP，永远不需要端口映射。** 这是 R1 的硬保障。

5. **主机切换 = epoch 递增 + 租约过期 + 新主机从其最新检查点冷启动。** 做不到 0 秒，但能做到"地址不变、自动恢复、卡的代价换稳定"。

6. **世界一致性用"快照 + 增量 + 原子提交"三件套。** 正常下线：暂停→保存→上传最终检查点→交接。崩溃：恢复到最近一次成功检查点，最多丢失一个检查点周期。

7. **模组兼容性是最大风险，不是协议问题而是"模组自身假设"问题。** 绝大多数服务端模组只关心"我运行在一个服务端进程里"，跟主机物理位置无关，因此可迁移；少数模组依赖本地路径/本地 DB/主机身份，需要黑名单。

## 2. 为什么公网节点"不需要 Minecraft"，以及它到底跑什么

很多人一听"服务器做中转"就想到 Velocity/BungeeCord。**那是错误的默认。** 我们来拆清楚。

### 2.1 三种"服务器角色"的本质区别

| 角色 | 是否解析 Minecraft 协议 | 是否需要游戏逻辑/世界 | 性能要求 | 我们的选择 |
| --- | --- | --- | --- | --- |
| 纯 L4 TCP 中继（Relay） | 否，只搬字节 | 否 | 极低（几 Mbps/玩家） | 主路线 |
| 协议代理（Velocity/BungeeCord） | 是，解析登录/握手/加密/插件通道 | 否，但需装服务端软件 | 中高 | 仅作可选增强 |
| 真实游戏服务端（Paper/Fabric Server） | 是，全量解析 | 是 | 高 | 永不放在公网节点 |

### 2.2 纯 L4 中继为什么能解决 R1

Minecraft Java 客户端连接就是一个 **TCP 长连接**（握手 → 登录 → 加密 → 配置 → 游玩）。只要有一条 TCP 管道从"玩家客户端"通到"主机上的服务端端口"，游戏就能跑，**中继根本不需要看懂里面是什么**。

管道怎么建？关键点：**所有连接都是玩家侧主动向外的出站连接。**

    Player A (client) ---> Relay (public) <--- Host B (agent, outbound)
       external conn            relay/pipe          reverse tunnel

- 主机 B 的 Agent 启动时，主动向 Relay 建一条**出站 TCP 长连接**，注册在 Coordinator 分配的虚拟地址/端口上。
- 玩家 A 连 Relay 的固定地址，Relay 发现"房间当前主机是 B"，于是把 A 的连接和 B 的反向隧道**对接（pipe）**。
- 全程 B 没有公网 IP、没做端口映射、NAT 后面也没关系。

这就是 R1 的完整技术答案：**不需要穿透配置，因为主机只做出站连接；不需要所有人有公网 IP，因为出口统一在 Relay。**

### 2.3 中继的两种实现形态（按你的服务器条件二选一）

| 形态 | 适用条件 | 实现 | 代价 |
| --- | --- | --- | --- |
| **有公网 IP（v4 或 v6）** | 服务器有独立地址 | 自研/自托管 Relay，直接监听 mc.example.com:25565 | 最好，延迟最低 |
| **啥都没有** | 内网机器/CGNAT/无固定 IP | 用 Cloudflare Tunnel / playit.gg / frp / rathole 把 Relay 端口暴露出去 | 多一跳，依赖第三方或自建内网穿透 |

**推荐：Relay 用 Rust 或 Go 自研，但"暴露"这一步用成熟隧道。**

- 服务器有 IP：Relay 自己监听即可。
- 服务器没 IP：跑一个 cloudflared / frpc 把 Relay 的本地端口暴露为公网 TCP。
  - 注意：Cloudflare 免费 Tunnel 的 **TCP 暴露能力有限、可能限速/限制端口**，做游戏实时流量要实测。**更稳的是自建 frp/rathole：一台公网小鸡当 frps，你的服务器当 frpc 出站接入。**
  - 如果连"公网小鸡"都没有，那就退一步用 playit.gg 这类托管隧道（有额外延迟和速率限制）。

结论：**"没有公网 IP"这个场景，本身就是用一条出站隧道把 Relay 暴露出去；主机侧永远是出站连接。** 所以你的两种服务器条件，架构上是统一的。

### 2.4 为什么主路线不选"公网节点跑 Velocity"

- Velocity/BungeeCord 需要理解 Java 协议、加密握手、online-mode 转发、模组插件通道。
- 大型整合包（Forge/NeoForge）握手极复杂，代理兼容性历史上一直是雷区。
- 最重要：**代理让公网节点变成"必须懂游戏、必须性能好、必须频繁升级跟随版本"的角色**——这正是你想消灭的成本。
- 所以：**MVP 用 L4 中继；协议代理只作为"未来可选增强"（见 §12）。**

### 2.5 另一种思路：公网节点连"服务端软件"都不装，它还需要什么

它需要的最小能力清单：

1. 一个 TCP 监听端口（接收玩家）。
2. 能维护"房间 → 当前主机隧道"的映射表（内存 + 少量持久化）。
3. 能处理主机心跳、租约、epoch（Coordinator 逻辑）。
4. 能存储世界检查点（磁盘或对象存储）。

这些全部是普通后端能力，**没有一行代码需要懂 Minecraft。** 这正是"公网服务器不需要 Minecraft"的严格证明。

## 3. 总体架构

### 3.1 组件图

                         +--------------------------------------+
                         |       Coordinator (public, no game)   |
                         |  rooms/members - host election         |
                         |  lease(epoch) - world version - signal |
                         +------------------+-------------------+
                                            | control channel (TLS/WS, outbound)
              +-----------------------------+-----------------------------+
              |                             |                             |
     +--------v--------+          +---------v--------+          +---------v--------+
     | Player A client |          | Host B Agent     |          | Host C Agent     |
     | (vanilla/modded)|          | + server process |          | + server process |
     +--------+--------+          +---------+--------+          +---------+--------+
              | TCP                         | reverse data tunnel (L4)      |
              |                             |                               |
              +-----------> +---------------v---------------+ <-------------+
                            |   Relay (public, no game)     |
                            |   port/mux - pipe             |
                            +---------------+---------------+
                                            |
                                 +----------v----------+
                                 | World Store (backup) |
                                 | checkpoints/deltas   |
                                 +---------------------+

### 3.2 三条连接通道（必须严格区分）

| 通道 | 端点 | 协议 | 用途 |
| --- | --- | --- | --- |
| 控制通道 | 玩家Agent ⇄ Coordinator | TLS + WebSocket/gRPC（**Agent 出站**） | 心跳、选举、租约、版本号、信令、日志 |
| 数据通道 | 玩家客户端 ⇄ Relay ⇄ 主机服务端 | **原始 TCP（L4 透传）** | 真正的游戏流量 |
| 同步通道 | 主机Agent ⇄ World Store | HTTPS/对象存储（**出站**） | 上传/下载检查点、增量 |

关键设计：**控制通道和数据通道分离。** 控制通道可以断线重连（用指数退避），不影响游戏；数据通道断线 = 玩家掉线重连。这决定了系统的故障域。

### 3.3 世界数据放哪？

三个选项，按你的成本偏好排序：

1. **公网节点的磁盘（推荐 MVP）**：检查点直接存 Coordinator/World Store 的磁盘。世界 10–30GB 也放得下，最省事。
2. **对象存储（S3/OSS/R2）**：放得下大世界，按量付费，适合后期。下载/上传走 HTTPS，不占中继带宽（如果玩家直连对象存储）。
3. **玩家间分片（不推荐做 MVP）**：世界分散在多个玩家机器上互相拉取，复杂度爆炸，仅作研究。

> **重要**：世界同步流量**不要走 Relay**，否则会和中继的游戏流量抢带宽。让主机直连 World Store（HTTPS）上传下载。

## 4. 核心机制设计（本文档重点）

### 4.1 主机选举与租约（防脑裂是命门）

**目标：任意时刻，房间里有且仅有一个 Active Host 能写世界。**

不能用简单的"谁先抢到谁当主机"，否则网络分区时会出现两个主机同时跑世界——存档直接损坏。

**方案：中心化租约 + epoch（fencing token）。**

- Coordinator 为每个房间维护：
  - epoch：单调递增整数，每次主机变更 +1。
  - lease：{host_id, epoch, expires_at}。
- Agent 加入主机角色时，必须先向 Coordinator 申请租约，拿到 (epoch, expires_at)。
- Agent 心跳续租（如每 2s，租约 10s）。续租失败或超时，租约作废。
- **关键规则：主机启动/继续服务端前必须持有有效租约；一旦发现自己的 epoch 落后，必须立即自杀（停止服务端），绝不允许旧主继续写。**
- 新主机用**更大的 epoch** 接管；World Store 拒绝来自过期 epoch 的写入（fencing）。

这套东西就是分布式存储里的标准做法（lease + fencing token），能从根本上杜绝脑裂。

**选举策略（可配置）：**

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| auto | 按评分排序：在线时长、历史主机成功率、上行带宽、CPU 核数 | 默认 |
| admin | 管理员在面板/群指令指定 | 关键局 |
| sticky | 优先上一任主机，避免频繁搬家 | 世界小、搬家贵 |
| manual | 完全手动，Agent 点击"我来当主机" | 调试 |

评分示例（权重可调）：

    score = w1 * uptime_minutes        // 越早来的越稳
          + w2 * (1 / recent_fail_rate) // 历史上没崩过的优先
          + w3 * log2(ram_gb)           // 机器越强越好
          + w4 * min(uplink_mbps, 100)  // 上行带宽（关键瓶颈）
          - w5 * current_player_count   // 差一个就在玩的人也会卡

### 4.2 主机切换流程（正常退出）

    Host B                    Coordinator                Host C             Player A
      |  "我要退出，开始交接"        |                         |                  |
      +-------------------------->|                         |                  |
      |                           | 冻结房间/标记 transferring |                  |
      |  1. 暂停接受新玩家          |                         |                  |
      |  2. /save-all flush        |                         |                  |
      |  3. 生成最终检查点 + 校验和   |                         |                  |
      |  4. 上传 World Store        |                         |                  |
      +-------------------------->|  记录 checkpoint vN      |                  |
      |                           |  选举 C 为主机, epoch+1   |                  |
      |                           +------------------------>|                  |
      |                           |                         | 下载检查点 vN     |
      |                           |                         | 启动服务端        |
      |   停止本地服务端             |                         | 注册反向隧道      |
      +-------------------------->|                         +----------------->|
      |                           |  Relay 把 A 的连接指向 C  |                  |
      |                           |                         |                  | A 重连
      |                           |                         |                  |

**玩家 A 的体验**：连接保持到 Relay 的固定地址不变；Relay 在切换时可能让 A 短暂断开，客户端重连后命中新主机。**不需要改地址、不需要手动操作。**

### 4.3 主机切换流程（崩溃/掉线）

    Host B 崩溃（没来得及交接）
       |
    Coordinator: 心跳超时(如 10s) -> 判定 B 失联 -> 租约作废 -> epoch+1
       |
    选举 C -> C 从 World Store 下载最近一次成功检查点 -> 启动服务端
       |
    玩家 A 断线 -> 客户端重连 -> Relay 指向 C
       |
    损失 = 最后一个检查点之后的所有进度（如 <= 5 分钟）

**优化：把"损失窗口"压到最小**——见 §4.4 增量同步。

### 4.4 世界同步：快照 + 增量 + 原子提交

**问题**：Minecraft 服务端持续在写 region 文件，**直接复制正在写的存档会得到损坏/不一致的结果**。必须在一致状态下复制。

**解决方案（三层）：**

1. **一致性快照（checkpoint）**
   - 正常路径：/save-all flush 让服务端把所有玩家数据与区块刷盘（会短暂卡顿），复制 world/、world_nether/、world_the_end/、playerdata/、server.properties、ops.json、whitelist.json 等。
   - 每次检查点计算**内容哈希**（Merkle 树或分块哈希），作为该版本指纹。
   - 打上 epoch 和 version。

2. **增量同步（deltas）**
   - 检查点之间只上传**变化的 region 文件块**（region 文件 .mca 是分块的，可以按 4KiB 扇区/区块粒度 diff）。
   - 用类似 rsync/内容寻址分块的方式做差分，降低上传量。
   - 心跳间隔（如 60s–5min）做一次轻量检查点，把崩溃损失窗口控制在心跳周期内。

3. **原子提交（atomic commit）**
   - 上传到临时路径 → 校验和比对 → **原子重命名**为正式版本。
   - 元数据（manifest.json）始终指向"当前有效版本"，绝不允许半成品被当有效版本。
   - 保留最近 N 个版本用于回滚。

**元数据示例：**

    {
      "room_id": "friends-smp",
      "version": 137,
      "epoch": 12,
      "created_at": "2026-10-08T12:00:00Z",
      "host_id": "player-B",
      "mc_version": "1.21.x",
      "loader": "neoforge-21.x",
      "modpack_hash": "sha256:...",
      "files": [
        {"path": "world/region/r.0.0.mca", "size": 4194304, "sha256": "..."},
        {"path": "world/level.dat", "size": 4096, "sha256": "..."}
      ],
      "checkpoint_type": "periodic",
      "previous_version": 136
    }

### 4.5 数据通道：反向隧道的具体实现

Relay 需要有"把外部连接 pipe 到某个已建立的反向隧道"的能力。核心数据结构：

    rooms[room_id]:
      current_host: host_conn      # 主机 Agent 保持的反向隧道
      epoch: 12
      pending_transfer: ...

    ingress:
      玩家连接到达 mc.example.com:25565
        -> 查 room -> 若 current_host 存在 -> pipe(player_conn, current_host_conn)
        -> 否则返回 "MOTD: 正在唤醒主机，请稍后重连"

实现要点：

- **连接复用**：主机 Agent 建立一条长连接，Relay 在这个 multiplex 通道上开逻辑子流（类似 yamux/smux）。每个玩家一个子流。
- **背压（backpressure）**：Relay 必须透传 TCP 背压，否则慢玩家会拖垮内存。用 copy_bidirectional 类原语，限制缓冲区。
- **超时与清理**：玩家断线、主机断线、半开连接都要有超时回收，避免 FD 泄漏。
- **0 RTT 重连（可选优化）**：客户端重连时，Relay 可缓存"MOTD/状态"信息，减少唤醒等待。

> 已经成熟的开源实现可直接借鉴：fatedier/frp、rathole-org/rathole、ngrok、cloudflare/cloudflared。**主机的"反向隧道"思想就是 frp 的 tcp + 反向代理模式。**

### 4.6 服务端进程管理（Agent 本地）

Agent 要做的事（跨平台，Windows 优先）：

1. **环境检测**：Java 版本、内存、磁盘余量、服务端 jar/模组目录。
2. **世界准备**：确认/下载世界版本，校验 manifest 哈希，拒绝版本错配启动。
3. **进程启动**：java -Xms.. -Xmx.. -jar server.jar nogui（或加载器启动脚本），捕获 stdout/stderr 做日志。
4. **健康检查**：进程存活、端口就绪、TPS/响应（可选）。
5. **优雅停止**：优先发 /stop 或 save-all flush + stop，再等待退出，超时才强杀。
6. **自动重启策略**：崩溃时按退避重启，但**必须重新走选举确认自己仍是主机**（防止旧 epoch 复活）。
7. **资源上报**：CPU/内存/磁盘/上行带宽，供选举评分。

### 4.7 版本与模组校验（防止"进去就崩"）

- 维护 manifest：Minecraft 版本、加载器版本、模组列表（文件名 + 哈希）、资源包、server.properties 关键项、白名单。
- 玩家加入前 pre-flight check：如果客户端模组/版本不匹配，Coordinator 直接拒绝并把差异清单发给玩家。
- **新主机启动前**必须校验 manifest，避免用旧世界配新模组启动导致世界升级不可逆。
- 世界格式升级（Minecraft/datafixer）要显式确认，且升级前自动打一个"升级前备份"。

### 4.8 状态机（Agent 视角）

            +----------+
            |  IDLE    |<----------- 未选定为主机
            +----+-----+
                 | 被选举
            +----v----------+
            |  PREPARING    | 下载世界 / 校验 manifest
            +----+----------+
                 | 世界就绪
            +----v----------+
            |  STARTING     | 启动服务端进程
            +----+----------+
                 | 端口就绪
            +----v----------+
            |  ACTIVE_HOST  | 服务中，周期检查点，续租
            +----+----------+
         +-------+-------------------+
         |       |                   |
      正常退出  租约丢失/心跳失败      崩溃
         |       |                   |
    +----v----+ +v-----------+  (进程退出)
    | DRAINING| | SELF_FENCE |
    | 保存交接 | | 立即停服    |
    +----+----+ +------------+
         |
    +----v----+
    |  IDLE   |
    +---------+

**SELF_FENCE 是安全底线**：只要 Agent 发现自己的 epoch 落后于 Coordinator，立刻停服，宁可不服务也不能双写。

## 5. 关键技术选型

| 层 | 候选 | 推荐 | 理由 |
| --- | --- | --- | --- |
| Relay / Coordinator 语言 | Go / Rust | **Rust（性能）；Go（开发快）** | 中继是关键路径，Rust 内存安全和性能好；Go 生态有 frp/yamux 现成件 |
| Agent 语言 | Go / Rust / Java | **Rust 或 Go（单二进制、跨平台）** | 与 Relay 共享隧道协议实现 |
| 服务端 | Vanilla / Paper / Fabric / NeoForge | **按整合包定** | Paper 兼容性好，模组包必须用对应加载器 |
| 隧道协议 | 自研 / frp / rathole / yamux | **yamux/smux 复用 + 自研控制层** | 复用成熟多路复用库，别重造 |
| 控制通道 | WebSocket / gRPC | **WebSocket + JSON/Protobuf** | 出站友好，穿透简单 |
| 世界存储 | 本地磁盘 / S3 兼容 | **MVP 本地磁盘，后期 S3** | 简单 |
| 增量同步 | rsync 式分块 / 内容寻址 | **内容寻址分块（CAS）** | 去重、可校验、可断点续传 |
| 认证 | 房间密钥 / 短期令牌 | **短期令牌 + 房间密钥** | 符合最小权限 |
| 打包 | Docker / 原生 | **原生单文件 + 可选 Docker** | 玩家机器上 Docker 不现实 |

## 6. 数据通道延迟与带宽分析（别被中继骗了）

中继**不增加主机上行带宽**。5–6 人模组服的带宽需求估算：

| 项 | 估算 |
| --- | --- |
| 每个玩家下行（服务端→玩家） | 10–100 KB/s（模组多时更高） |
| 每个玩家上行（玩家→服务端） | 小，几 KB/s |
| 主机上行需求 | 约等于 Σ 玩家下行 = 0.5–5 Mbps（视模组） |
| 中继节点带宽 | 约等于双向总和，需 >= 主机上行 × 玩家数 / 分流 |

结论：
- **中继节点的出口带宽是硬成本**，比 CPU/内存更重要。
- **主机家宽上行是硬瓶颈**，中继无法救。若主机上行 < 10Mbps，5–6 人模组服会卡。
- 延迟：同区域中继额外延迟通常 5–30ms。跨区域会明显变差。

**优化手段：**
- **优先直连**：如果主机能开端口（UPnP/有公网），让玩家部分直连，Relay 只做备用。类似 World Host 的"先 UPnP 失败再走代理"策略。
- **就近接入**：Relay 多区域部署，玩家连最近的 Relay。
- **UDP 旁路**：语音模组走 UDP，TCP 中继覆盖不到，需要单独方案（见 §9）。

## 7. 风险评估与对策（诚实清单）

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 脑裂导致存档损坏 | 高 | 中心化租约 + epoch fencing + SELF_FENCE |
| 世界复制不一致/损坏 | 高 | 只复制一致快照；校验和；原子提交；保留多版本 |
| 模组假设主机身份/本地路径 | 中 | 兼容性测试矩阵 + 黑名单 + 明确不支持清单 |
| 主机上行不足 | 中 | 直连优先 + 就近中继 + 明确带宽告知 |
| 公网节点无固定 IP/无公网 | 中 | frp/rathole/Cloudflare 隧道 + 出站连接 |
| 客户端版本/模组不一致 | 中 | pre-flight 校验 + 拒绝进入 + 差异清单 |
| 崩溃损失窗口 | 中 | 缩短检查点周期 + 增量同步 |
| 语音/自定义 UDP | 中 | UDP 旁路或第三方语音服务 |
| 认证/授权被绕过 | 高 | 短期令牌 + 最小权限 + 备份加密 |
| 中继被 DDoS/滥用 | 中 | 限速、连接数上限、令牌校验 |

## 8. 分阶段实现路线（能动手的粒度）

### Phase 0 —— 打通"中继 + 单一主机"（1–2 周量级）

- [ ] Relay（Rust/Go）：监听端口，把外部连接 pipe 到一条反向隧道。
- [ ] Agent 最小版：出站连接 Relay，把本地 25565 挂上去。
- [ ] 一个玩家当固定主机，其他玩家连 Relay 地址能进。
- **验收**：3 人进同一个世界，稳定 30 分钟。

### Phase 1 —— Coordinator + 选举 + 世界同步

- [ ] Coordinator：房间、成员、心跳、租约、epoch。
- [ ] Agent：自动下载世界、启动/停止服务端、周期检查点。
- [ ] World Store：快照 + 原子提交 + manifest。
- **验收**：指定主机 A 下线，B 自动接管，玩家重连后世界连续。

### Phase 2 —— 崩溃接管 + 增量同步

- [ ] 心跳超时检测 → 自动重选举。
- [ ] 增量同步把损失窗口压到 <= 心跳周期。
- [ ] 回滚 UI/指令。
- **验收**：强杀主机进程，90 秒内新主机恢复，回滚 <=5 分钟。

### Phase 3 —— 体验与增强

- [ ] 就近中继、直连优先（UPnP）。
- [ ] 管理面板、通知、备份策略。
- [ ] 评估 Minecraft Transfer 机制 / 协议代理（见 §12）。
- [ ] 模组兼容性矩阵与自动 pre-flight。

## 9. 特殊坑位详解

### 9.1 UDP（语音模组）

Simple Voice Chat 等走 UDP，L4 TCP 中继覆盖不到。选项：
- 语音走独立 UDP 中继（frp 支持 UDP）。
- 改用外部语音（Discord/QQ）。
- MVP 先不支持，文档明确标注。

### 9.2 正版验证 vs 离线账号

- online-mode=true：登录走 Mojang 会话验证，中继不参与，透传即可（**注意：不要在中继做 MITM 解密**）。
- 离线账号：需要 online-mode=false，需自行做白名单/密码，安全自担。
- **不要在 Relay 解密玩家流量**——保持纯 L4 透传，避免安全责任和性能开销。

### 9.3 server.properties 里与迁移相关的键

- level-name：世界目录名，迁移要一致。
- online-mode：见上。
- pause-when-empty-seconds：无人时暂停，省资源（对"没人时省电"有帮助）。
- accepts-transfers：如果用官方 Transfer 机制，目标服需设 true。
- view-distance / simulation-distance：直接影响主机 CPU 与带宽，迁移后应保持一致。

### 9.4 玩家数据（playerdata)与进度

- 玩家背包/进度存在 world/playerdata/*.dat 和 advancements/、stats/。
- 这些必须随世界一起同步，否则切换后"回到上辈子"。
- 注意：玩家在线时服务端可能还没落盘，save-all flush 会强制刷盘。

### 9.5 世界大小与首次下载时间

- 大型整合包世界可能 10–50GB。新主机首次接管要下载全量，耗时可能几分钟到几十分钟。
- 对策：**预下载**——Coordinator 提前让"候选主机"在后台同步世界，做到切换时"热插拔"。
- 用 BT/分块 P2P 加速大世界分发（后期）。

## 11. "公网服务器不需要 Minecraft" 的最终确认

再强调一次，因为这是你最在意、也最省钱的点：

- **Coordinator**：只用 HTTP/WS + 一个小数据库（SQLite 足够），无游戏逻辑。1 核 512MB 可跑。
- **Relay**：只搬运 TCP 字节，无游戏逻辑。CPU 极低，瓶颈是带宽。
- **World Store**：只存文件，可用磁盘或对象存储。
- **Minecraft 本体只出现在玩家机器上**（由 Agent 启动的服务端进程）。

**核心成本 = 公网节点带宽。** 只要带宽够，算力全在玩家侧，这就是本方案的经济性来源。

## 12. 未来可选增强（不进入 MVP）

1. **协议感知代理 / 官方 Transfer 机制**
   - Minecraft 1.20.5+ 有 transfer 包和 accepts-transfers，可让服务端主动把玩家转给新主机。
   - Cookie 可跨转移携带 <=5KiB 小数据（可用于会话续接），但**不能承载世界**。
   - 优点：重连更平滑、可显示提示；缺点：仍是一次断连重连，且旧版本/部分模组不支持。
   - 结论：作为"体验优化"而非"架构依赖"。

2. **直连优先 + 中继兜底**（类 World Host）：能 UPnP 成功就直连，降低中继带宽和延迟。

3. **多区域 Relay + 就近接入**。

4. **P2P 分块世界分发**：新主机用 BitTorrent 式从多个现有玩家拉世界，加速大世界热备。

5. **真分布式模拟**（多机算区块）：**明确排除出 MVP**，这是另一个量级的研究项目。

## 13. 一句话给未来的自己

> 公网节点只做两件事：**记状态、搬字节**。世界和算力永远在玩家机器上轮流活。
