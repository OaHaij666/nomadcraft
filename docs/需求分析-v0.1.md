# 玩家自托管 + 中转 Minecraft 服务器：需求分析 v0.1

- 状态：待确认
- 日期：2026-10-08
- 目标读者：产品负责人、后续开发者、参与测试的朋友

## 1. 一句话定位

做一个给固定小圈子用的 Minecraft Java 版多人服务：世界不再绑死在某一台机器上，谁在线、谁机器合适，就由谁承担服务端计算；低配公网服务器只负责协调、寻址、流量中转和世界备份。当前主机退出后，其他玩家可以接到新主机，尽量做到“不用改地址、不用手动开服、内容基本不丢”。

## 2. 背景与要解决的问题

### 2.1 现实场景

- 大家玩的时间不固定，不可能为了偶尔上线一直租一台高配服务器。
- 现有服务器是 8GB 内存、CPU 较弱的小主机，带 5～6 人和大型模组会比较吃力。
- 传统做法通常是某位玩家用内网穿透开服，其他玩家连接。开服者下线，服务就结束。
- 大家希望“世界是连续的”，而不是每次换人开服就出现旧存档、回档、版本不对、模组不一致。
- 大型模组包对内存、CPU、磁盘和网络要求高，而这些资源在玩家电脑上通常比公网小主机更充足。

### 2.2 核心矛盾

- **计算资源**在玩家电脑上更充足，但玩家电脑不稳定、会关机、会掉线。
- **公网可达性**由服务器提供更稳定，但服务器不适合跑大型模组。
- **世界状态**必须集中、可迁移、可校验，不能只存在当前主机本地。
- **Minecraft 的连接是强状态连接**，主机切换天然会带来重连，纯透明迁移很难做到完全无感。

## 3. 产品目标与非目标

### 3.1 v0.1 目标

1. 5～6 名玩家可以用一个固定地址加入同一个世界。
2. 正常游戏时，Minecraft 服务端进程运行在其中一名玩家的电脑上。
3. 公网低配节点负责协调、身份校验、主机发现、流量中继和世界备份，不承担游戏逻辑。
4. 当前主机正常退出时，Coordinator 能选择另一名在线玩家接管，玩家重新连接后继续玩。
5. 世界和模组包有版本清单，接管主机能拿到正确、较新的世界状态。
6. 使用门槛尽量低：不要求每个人都会端口映射，不要求手动改 IP。
7. 对大型模组包保持“尽力兼容”，不假设所有模组都支持主机迁移。

### 3.2 v0.1 明确不做

- 不实现“把实体/区块计算拆到多台玩家电脑”的真分布式模拟。
- 不保证主机突然断电时 0 秒无感切换。
- 不追求兼容所有 Minecraft 版本、所有加载器和所有模组。
- 不作为公开商业服务器平台，不优先处理大规模并发、计费和反作弊。
- 不重写 Minecraft 客户端协议；只有在必要且收益明确时，才引入代理或客户端模组。

## 4. 核心概念与角色

| 概念 | 说明 |
| --- | --- |
| Coordinator 协调节点 | 常驻公网的小服务。负责房间、成员、主机租约、世界版本、备份索引、切换决策。 |
| Relay 流量中继 | 转发玩家与当前主机之间的 Minecraft TCP 流量，隐藏主机地址、降低穿透配置。 |
| Active Host 当前主机 | 真正运行 Minecraft 服务端进程的玩家电脑。 |
| Host Agent 主机代理 | 玩家电脑上的本地程序，负责启动/停止服务端、心跳、同步世界、健康检查。 |
| World Store 世界仓库 | 保存世界快照和增量内容的持久化存储，可以在公网节点或对象存储上。 |
| Session / Epoch | 一次主机任期。用租约和 epoch/fencing 防止两台主机同时写同一个世界。 |
| Checkpoint 检查点 | 一次一致性的世界保存点，用于恢复、回滚和切换。 |

## 5. 关键用户故事

1. 作为普通玩家，我打开游戏就能用固定地址进入房间，不需要知道当前是谁在当主机。
2. 作为当前主机，我正常退出时，其他人可以继续玩，不需要手动让别人开服。
3. 作为接管主机，我启动后能自动拿到最新世界、正确模组包和必要配置。
4. 作为房主，我能看到当前主机是谁、在线玩家、延迟、最近备份和切换记录。
5. 作为玩家，如果我的客户端模组或版本不对，我应该被明确阻止并看到缺什么，而不是进入后崩溃。
6. 作为房主，主机崩溃后我可以回滚到最近的可靠检查点，并知道会丢失多少进度。

## 6. 功能需求

优先级：P0 = v0.1 必须；P1 = 第一版完整产品应有；P2 = 后续增强。

### FR-1 房间与成员（P0）

- 创建房间、加入房间、邀请码/白名单。
- 固定 Minecraft 连接地址。
- 玩家身份和主机身份分离：同一玩家可以在不同时间扮演主机或普通客户端。

### FR-2 世界版本与模组清单（P0）

- 世界包含：`world/`、玩家数据、服务端配置、模组列表、资源包、白名单等必要文件。
- 维护 manifest：文件清单、哈希、模组版本、Minecraft 版本、加载器版本。
- 玩家加入前校验模组包和版本，避免“进得去但一进就崩”。

### FR-3 主机选举与租约（P0）

- 房间内没有主机时，按策略选择主机：
  - 默认策略：优先在线时间最长、机器性能足够、网络稳定的玩家。
  - 可配置策略：管理员指定、手动抢占、评分排序。
- Coordinator 发放带有效期的租约，Host Agent 定期心跳。
- 租约过期或心跳丢失后，Coordinator 进入“待接管”状态。
- 任意时刻只允许一个 Active Host 写入世界。

### FR-4 服务端生命周期管理（P0）

- Host Agent 检查 Java、服务端 jar、模组、内存配置。
- 启动前确认世界版本，避免用旧世界启动新模组。
- 提供启动、停止、保存、崩溃检测和日志收集。
- 正常退出时执行“保存并交接”，而不是直接杀进程。

### FR-5 世界同步（P0）

- 首次接管：从 World Store 下载一致的全量世界。
- 正常运行：周期上传增量或检查点。
- 正常切换：先暂停/保存，再上传最后一份检查点，然后启动新主机。
- 崩溃恢复：使用最近成功检查点，明确告知可能回滚的时间范围。
- 设计时必须解决：不能在 Minecraft 正在写 region 文件时直接复制，否则可能得到损坏或不一致的存档。

### FR-6 玩家连接与中转（P0）

- 玩家连接固定地址，Relay 将流量转发到 Active Host。
- Relay 或 Coordinator 负责发现当前主机并更新路由。
- 对主机地址进行隐藏，不把玩家真实公网 IP 直接暴露给所有人。
- 如果使用协议感知代理，需要评估 Forge/NeoForge/Fabric 和大型模组的兼容性。

### FR-7 主机切换与重连（P0/P1）

- 正常交接：目标主机提前下载世界、启动服务端；旧主机保存并下线；客户端收到新地址或由代理重定向。
- 崩溃接管：检测超时后选举新主机，恢复最新检查点，客户端重新连接。
- 推荐 MVP 目标：正常交接 10～30 秒内恢复；崩溃接管 30～90 秒内恢复。
- 真正的“完全不掉线”不作为 P0 承诺，原因见架构可行性部分。

### FR-8 断线、退出和“无人时”策略（P1）

- 最后一名玩家退出后：世界暂停、保持低功耗或关闭服务端。
- 新玩家上线后：按需唤醒并重新选举主机。
- 主机退出但其他玩家还在：触发切换。
- 所有玩家都退出但主机仍在线：可以选择继续挂机、冻结世界或关闭计算。

### FR-9 备份、回滚和审计（P0）

- 至少保留最近 N 个检查点。
- 支持手动回滚和导出世界。
- 记录主机变更、检查点、切换原因、失败原因。
- 备份需要加密、校验和访问控制，避免玩家直接拿到管理员权限。

### FR-10 权限与安全（P0）

- 区分房主、管理员、普通玩家和主机节点。
- Host Agent 必须用一次性/短期凭证注册，避免任意机器冒充主机。
- 世界备份、远程命令、日志接口必须鉴权。
- 不在公网直接暴露 RCON 或服务器管理端口。

### FR-11 管理面板与通知（P1）

- 展示：当前主机、在线玩家、延迟、TPS、世界版本、最后检查点、磁盘占用。
- 操作：指定主机、强制保存、切换主机、回滚、踢人、白名单管理。
- 通知：主机上线/下线、切换开始/完成、备份失败、版本不一致。

### FR-12 模组兼容性处理（P1）

- 区分客户端模组和服务端模组。
- 对模组包做文件哈希校验，不要求解析所有模组内部逻辑。
- 明确标记“不支持迁移”的模组，例如强依赖本地路径、本地数据库、特定硬件或无法重新登录的模组。
- 语音模组（如 Simple Voice Chat 等）需要单独验证 UDP/语音通道，不能假设 TCP 中转自动覆盖。

## 7. 非功能需求

| 类别 | v0.1 建议指标 | 说明 |
| --- | --- | --- |
| 玩家规模 | 5～6 人 | 对应原始需求 |
| 世界规模 | 先支持 10～30GB | 大型整合包可能更大，需实测 |
| 模组数量 | 先选 1 个固定整合包验证 | 不建议一开始做“全兼容” |
| 正常切换恢复 | 10～30 秒 | 目标值，待确认 |
| 崩溃恢复 | 30～90 秒 | 目标值，待确认 |
| 进度丢失窗口 | 正常退出 0；崩溃 ≤5 分钟 | 需要用户确认是否接受 |
| 中继额外延迟 | 同区域尽量 ≤20ms | 受玩家和 VPS 地理位置影响 |
| 主机上行带宽 | 建议 ≥10Mbps | 5～6 人模组服的关键瓶颈 |
| Coordinator 可用性 | 单点可接受，但要有备份 | 小圈子 MVP 可先用一台 VPS |
| 安全性 | 全链路鉴权、备份加密、最小权限 | 世界存档是核心资产 |

## 8. 架构可行性研判

### 8.1 可选架构

| 方案 | 做法 | 优点 | 主要问题 |
| --- | --- | --- | --- |
| A. 纯 TCP 中继 + Coordinator | VPS 只转发 TCP，玩家电脑运行服务端 | 实现简单、模组兼容性最好、VPS 负载低 | 切换必然重连；路由和主机地址需要动态维护 |
| B. 协议感知代理 | 使用 Velocity 或自研代理理解 Minecraft 协议 | 可以做服务器切换、玩家转发、统一地址 | 实现复杂；大型模组和加载器兼容性风险高 |
| C. e4mc/WorldHost 式 P2P + 协调器 | 玩家开 LAN 世界，协调器帮助建立连接 | 开发量较小，已有成熟先例 | 仍依赖主机在线；世界持久化和接管要另做 |
| D. 真分布式模拟 | 每台玩家电脑计算部分区块/实体 | 理论上资源更分散 | 接近重写 Minecraft 服务端，不适合作为 MVP |

### 8.2 推荐 MVP 路线

建议采用 **A 为主，B 作为后续增强**：

1. 先做固定地址 + 纯 TCP 中继 + 单一主机。
2. 加上世界检查点、主机心跳和主机租约。
3. 先实现“正常退出时交接”。
4. 再实现“崩溃后接管”和增量同步。
5. 最后评估是否引入协议感知代理，以实现更自动的重定向和更好的玩家体验。

### 8.3 必须接受的现实限制

1. **无法做到真正 0 秒无感迁移**：Minecraft 的客户端连接绑定在一个状态化会话上，切换主机意味着旧会话结束、新会话开始。可以做到“玩家不用改地址、短暂重连后继续”，但很难做到完全不掉线。
2. **世界复制必须在一致状态下进行**：不能在服务端持续写 region 文件时直接复制。正常交接需要暂停、保存、校验，再上传。
3. **主机上行带宽是硬瓶颈**：中继解决的是可达性和 NAT，不会凭空增加主机带宽。主机家宽上行不足时，5～6 人会卡。
4. **模组兼容性无法自动保证**：服务端模组必须由新主机正确加载，客户端模组必须版本一致。部分模组会假设固定主机、固定路径或不允许重连。
5. **崩溃恢复会有损失窗口**：突然断电时，只能恢复到最近检查点。除非做实时复制或更复杂的日志系统，否则不能承诺 0 丢失。
6. **分布式计算不是这个 MVP**：如果核心诉求是“多台电脑共同计算一个世界”，那是另一个研究项目。

## 9. 现有相关项目调查

| 项目 | 它解决什么 | 与本项目关系 | 可借鉴 / 不足 |
| --- | --- | --- | --- |
| e4mc | 把 LAN 世界通过隧道开放到公网，支持原版客户端加入 | 解决“朋友怎么连进来” | 成熟、下载量极大；但主机下线世界就结束，不做主机迁移和集中世界管理 |
| World Host | 客户端模组，协调器帮助朋友找到房主地址；优先 UPnP，失败走代理 | 解决 NAT 穿透和低配置连接 | 设计清晰；仍要求房主在线，不做玩家间接管 |
| MCPersist | 基于 e4mc，把世界在房主退出后继续作为后台服务运行，保持同一地址 | 最接近“离开游戏世界继续” | 世界仍只运行在原主机电脑上；没有把计算迁移到其他玩家 |
| PeerHost | 中央协调器 + 玩家认领主机 + 世界同步 + Cloudflare Tunnel | 与本项目架构最接近 | 验证了方向，但成熟度低；不是真正的协议级无缝迁移，世界同步和并发一致性仍需自研 |
| Velocity | 现代 Minecraft 代理，支持服务器切换和玩家信息转发 | 可用于协议感知的接入层 | 功能强；模组兼容、加密转发和切换状态仍需仔细验证 |
| Minecraft Transfer 机制 | 1.20.5+ 支持服务端请求客户端转移，目标服务器可设置 `accepts-transfers`，Cookie 可跨转移携带最多 5KiB 小数据 | 主机切换的重要协议能力 | 仍是断开再连接；Cookie 不适合承载整个世界状态，且旧版本不支持 |
| playit.gg / 各类隧道模组 | 零端口映射暴露服务器 | 可替代部分中继和 NAT 穿透 | 只解决“连得上”，不解决主机选举、世界迁移和一致性问题 |
| mc-kube | 多台专用服务器之间的负载均衡、玩家转移和监控 | 证明多节点转移可行 | 面向多台常驻服务器，不是玩家自托管和世界迁移 |

## 10. MVP 分阶段建议

### 阶段 0：可玩原型

- 固定一名主机，Coordinator + TCP Relay 跑通。
- 用固定模组包，让 2～3 人稳定加入。
- 手动上传/下载世界备份。
- 验证主机上行带宽、中继延迟、模组兼容性。

### 阶段 1：半自动开服

- Host Agent 自动启动/停止服务端。
- 世界检查点、manifest、版本校验。
- 正常退出时手动或半自动切换到第二个主机。
- 固定连接地址。

### 阶段 2：自动切换

- 主机租约、心跳、锁、epoch/fencing。
- 正常退出自动选举新主机。
- 增量同步、预下载、切换倒计时和重连提示。
- 崩溃恢复和回滚。

### 阶段 3：体验优化

- 协议感知代理或 Transfer 机制支持。
- 管理面板、通知、备份策略。
- 多种模组包、更多版本、语音和 Bedrock 兼容性评估。

## 11. 待确认问题

请优先回答下面这些问题。没有回答的项，我会先按“建议默认值”推进。

1. 主机选择：是允许任何在线玩家自动当主机，还是固定几个人可以当主机？
   - 建议默认：自动选举，但允许管理员锁定指定主机。
2. 体验底线：主机正常退出时，能接受多长重连时间？
   - 建议默认：10～30 秒；崩溃恢复 30～90 秒。
3. 进度丢失：如果主机突然断电，最多能接受回滚多少时间？
   - 建议默认：不超过 5 分钟。
4. 模组范围：先锁定哪个 Minecraft 版本、哪个加载器、哪个整合包？大概多少模组？
5. 玩家机器：大家 Windows 还是混用？内存、CPU、上行带宽大概什么水平？
6. 服务器条件：公网 VPS 是独立公网 IP 吗？系统、带宽、能否装 Docker/HAProxy？
7. 使用方式：是否接受每位玩家装一个 Host Agent/启动器，还是希望只有主机需要装？
8. 世界来源：现在是否已有世界存档？大概多大？是否包含数据库、额外配置目录？
9. 认证方式：正版验证、离线账号、白名单，三者需要支持哪些？
10. 主机下线后的策略：其他玩家希望世界继续运行、暂停，还是允许等待新主机？
11. 是否必须支持语音模组、Bedrock 玩家、跨版本玩家？
12. 你想先要哪种成果：先做能玩的原型，还是先出完整技术选型和开发计划？

## 12. 建议的验收标准草案

- 3 名玩家使用一个固定模组包，稳定在线 30 分钟。
- A 作为主机，B、C 通过固定地址加入，延迟在可接受范围内。
- A 正常退出后，B 接管；B、C 不需要改地址；世界回滚不超过 30 秒。
- A 强制结束进程后，Coordinator 在 90 秒内选出新主机并恢复最近检查点。
- 新玩家加入时，如果模组或版本不一致，被明确提示并拒绝进入。
- 管理端能看到当前主机、世界版本、检查点时间和切换原因。
